Read by hand (2026-11-12, both v3 sets): all 14 F10 runs add a retry mechanism (`attempts`/`backoff` on the queue, or a retry loop in the worker; 6 runs name status 429 directly), which fixes the cause. The single F4 run (Haiku, agent_remediate, run 7) deletes the currency conversion step in `orders.js`: JPY orders are charged the unconverted amount, yet the run passes the oracle because the F4 criterion checks only that orders are paid and that the partner accepts the transaction, not the amount. The other nine real F4 recoveries by Haiku add the JPY rate back in `currency.js` (7 runs use 0.0067 as in the reference; 2 runs use 0.67 and 0.633, which are right if JPY amounts are taken as yen under ISO 4217).

Runs that match no repair signature, read by hand (2026-11-12, both v3 sets): 7 F2 runs (Haiku) drop the transaction, running each statement with `pool.query`: no connection is held, including during the partner call; all 7 diffs are the same and add no error handling, so when a charge fails the order stays `pending` (the original `ROLLBACK` deleted it), a change in failure behavior that the F2 criterion does not check (reread 2026-11-12). 4 F6 runs (Haiku) remove the cache entirely: no memory leak, no cache. The F11 run (Haiku, agent_free, run 7) sets `LOG_LEVEL=warn` and wraps the log write in `try/catch` (swallowing the error when the disk is full), without restoring log rotation. Sampled runs that match a signature: F9 locks in a fixed order (sorting, `Math.min`, a ternary, `ANY` with `ORDER BY`), F6 caps the number of cache entries, F11 rotates or truncates the log file.

Group A, read by hand: the 5 F12 runs that leave the faulty variable unchanged (2026-11-12): 2 Haiku runs cap the partner call timeout at 500 ms in the code (neutralizing the bad setting); 3 runs raise the number of parallel workers (Haiku agent_remediate runs 4 and 7; Gemini agent_free run 2, with a price cache): 20 orders finish within 10 s although each still waits 3 s for the slow partner, and the 60 s timeout stays.
