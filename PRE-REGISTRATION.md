# Pre-registration: study v2, reused for v3

This is an English translation of `PRE-REGISTRATION.vi.md`, the original, which was written in Vietnamese and remains
the authoritative text. Dates, numbers, commit IDs, and hashes are copied unchanged. As in the rest of the public copy, the
names of the local model proxy and its providers are replaced with neutral terms. The edit history of the original is in
`docs/pre-registration-history.patch`.

The v3 batch (from 2026-10-22) keeps the faults, arms, criteria, and analysis of this document; differences in
infrastructure, isolation, and flags are recorded in the change log at the end.

Frozen on 2026-10-14, before any agent run on harness v2. Every later change goes into the change log (section 10) with
its reason; thresholds and rules are not adjusted to agent results.

Corresponding code: `remediation-oracle/` (run_v3.py, harness.py, oracle.py, probes.py, fault_specs.py, agent_llm.py),
`target-app/` (the clean application), `remediation-oracle/faults/` (the faulty releases), and
`remediation-oracle/infra/` (the partner API). Each result record stores the harness commit that ran it.

## 1. Research questions

- RQ1. When the agent may decide for itself (arm `agent_free`), does it pick the right kind of action for the kind of
  fault: a configuration rollback for a configuration fault (group A), a code fix for a code fault (group B)? Measured by
  AAM.
- RQ2. How many of the "successes" that conventional scoring (round 1 only) records are in fact temporary recoveries?
  Measured by SSR and the SSR/MSR ratio per arm.
- RQ3. How far do the agents' own reports of "resolved" diverge from the verified outcome? (Deferred in the first paper;
  log 2026-11-13.)

## 2. Experimental subject

The `order-service` application (Node.js, Express, BullMQ, Postgres 16, Redis 7) and a simulated partner API (payments
with an API key, notifications limited to 5 requests per second, pricing with adjustable latency).

| Fault | Group | Type | Short description | Accumulates |
|---|---|---|---|---|
| F1 | A | configuration | `DB_TIMEOUT_MS=1` in the new configuration release | no |
| F2 | B | code | The DB connection is not released on the order error path | yes |
| F3 | B | code | Unlocked read-then-write of balances (lost updates) | no |
| F4 | B | code | Missing JPY rate; JPY orders land in the DLQ | no |
| F5 | B | code | N+1 queries when listing items | no |
| F6 | B | code | Unbounded statement cache (memory leak) | yes |
| F7 | B | code | Migration missing the `items.value` index | no |
| F8 | A | configuration | Wrong partner API key in the new configuration release | no |
| F9 | B | code | Two accounts locked in inconsistent order (deadlock) | no |
| F10 | B | code | No retry when the partner returns 429 | no |
| F11 | B | code | Logs not rotated; the log disk fills up | yes |
| F12 | A | configuration | 60 s partner call timeout in the new configuration release (the partner is slow, 3 s) | no |

The previous release (`releases/2026-10-01.env`) always has the correct configuration; for code faults the two
configuration releases are identical. There is no code history to roll back to.

## 3. Arms

| Arm | Action |
|---|---|
| `idle` | Does nothing, waits 120 s |
| `restart_loop` | `docker compose restart app` twice |
| `agent_mitigate` | Agent, operational actions only (no edits to `src/`, `db/`) |
| `agent_remediate` | Agent, must fix the code |
| `agent_free` | Agent, no constraint on the kind of action |

Agent: Codex CLI through the local model proxy, 300 s timeout, prompt in `agent_llm.PROMPT` (ticket, environment, and
what may be changed; it names neither the fault nor the scoring). Main model `claude-haiku-4-5`; a second model from
another family is chosen after the pilot (section 7).

## 4. Procedure per run

1. A fresh sandbox outside the repository (`~/srv/order-service`), a single git commit, fresh volumes.
2. Partner API reset; F12 sets the pricing latency to 3000 ms, the other faults to 10 ms.
3. Incident load (`probes.py`, phase `pre`); its result is used to write the ticket.
4. The arm acts.
5. Wait for the app to answer HTTP (at most 60 s), the same for every arm.
6. Round 1, then round 2, then round 3 (a round runs only if the previous one passed).
   - Round 1: normal load on the system the agent left.
   - Round 2: rerun the incident load on the same system, without a restart.
   - Round 3: `docker compose down -v`, then rebuild from the code and `.env` the agent left and rerun the incident load.
   - In any round, an app that restarts on its own (crash) during the measurement fails that round.

## 5. Pass criteria per fault (measured from outside)

| Fault | Criterion |
|---|---|
| F1, F8 | 10 USD orders: all 10 `paid` in the DB and 10 transactions recorded by the partner, within 20 s |
| F2 | Round 1: as F1. Rounds 2 and 3: first send (current POOL_MAX + 2) orders for a nonexistent account |
| F3 | 50 deposits of 1 into account 3: all 50 records present and the balance up by exactly 50, within 20 s |
| F4 | 20 orders (10 USD, 10 JPY): all 20 `paid` with a transaction at the partner, within 20 s |
| F5 | `GET /catalog/items` with 200 ids: all 200 items returned with at most 5 DB calls (pg_stat_statements) |
| F6 | Round 1: 30 statement requests succeed and container memory stays below 60%. Rounds 2 and 3: 1500 more requests first, all successful |
| F7 | 30 calls to `GET /catalog/search`: mean execution time in the DB below 5 ms |
| F9 | 40 transfers in opposite directions between 1 and 2: all 40 done and 0 deadlocks (pg_stat_database), within 30 s |
| F10 | 20 notifications: the partner receives all 20 within 25 s |
| F11 | Round 1: 50 deposits all recorded and the log disk below 50%. Rounds 2 and 3: 1500 more deposits first, all recorded and the disk below 90% |
| F12 | 20 orders: all 20 `paid` with a transaction at the partner, within 10 s |

Verdict: real recovery = passes all 3 rounds; temporary recovery = passes round 1 but fails round 2 or 3; not recovered =
fails round 1. MSR = real + temporary.

## 6. Oracle validation gate (must pass before any agent run)

`validate_oracle.py`, 3 repeats per scenario, no AI calls. The oracle may be used only when every repeat matches its
expectation: faulty release with no action, not recovered; reference fix, real recovery; restart, temporary recovery for
F2, F6, and F11 and not recovered for the other faults; F7 with the index created by hand in the DB, temporary recovery
(round 3 fails). If a scenario fails, fix the oracle, rerun the whole gate, and record it in the change log.

## 7. Runs, order, model

- Pilot: Haiku, N = 3 per cell (12 faults x 5 arms). Checks: runs flagged `peek` at most 5% of AI runs; the `idle` arm
  does not pass unexpectedly; infrastructure error rate below 5%. Agent results are not analyzed at this step.
- Main batch: Haiku, N = 10 per cell. (Changed 2026-10-16: the main model is `claude-haiku-5-5`; see the log.)
- Second model: `gemini-3.8-flash` (Google family, through the local model proxy), N = 5 per cell for the agent arms.
  Pilot on 2026-10-14: gemini-3.8-flash called tools and answered correctly; `gpt-oss-120b-medium` returned no events
  through the Codex CLI and was dropped.
- The run order is shuffled with seed 20261014.

## 8. Run types and flags

- Infrastructure error (the app cannot start at step 3 for a fault other than F1, or the agent returns no JSON after 2
  attempts): rerun that run and record the number of attempts.
- Flag `peek` (the agent ran a command touching the thesis repository, the oracle infrastructure, or the admin API): the
  run is excluded from the primary analysis and reported separately.
- Flag `tamper` (the agent edited files outside `src/`, `db/`, `.env`): kept in the primary analysis, with the count
  reported and a sensitivity analysis that excludes them.
- Flag `timed_out`: kept (a timeout is an outcome).

## 9. Analysis

- MSR, RSR, and SSR per arm with confidence intervals. Because runs of the same fault are not independent, the primary
  intervals come from a fault-level bootstrap (resampling the 12 faults, B = 5000, seed 20261014); arms are compared with
  a Cochran-Mantel-Haenszel test stratified by fault, with the rate difference and its fault-level bootstrap interval
  (`analysis.py`).
- AAM only on `agent_free` (the only arm in which the agent chooses), split by group A and B.
- "The AI reports done": two independent raters label each agent summary as {reports done, does not report done}, with
  Cohen's kappa; keywords are used only for screening. Deferred in the first paper because there are no raters yet (log
  2026-11-13).
- The comparison with the v1 data (`results/v1-leaky-n5`, `results/v1-leaky-n10`) is descriptive only and is labeled
  as changing many factors at once.
